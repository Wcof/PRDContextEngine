# ADR 0008: PM Thinking Loop Internalization — 心智链 + 流程链双层注入

## Status

Accepted (2026-06-29). **Superseded in part by [ADR 0016](0016-explicit-process-artifacts.md) (2026-07-06)**: 本 ADR 中「`.loop/` 隐藏 + gitignore + Wipe-on-Entry 删除」部分已被推翻，过程文档迁至显性 `process/`、进版本库、重跑改归档。下列涉及 `.loop/` 的措辞为历史注记，现行实现以 ADR 0016 为准。本 ADR 其余部分（心智链 6 步、双层注入模型、审计三元组、自愈机制）不变。

## Context

PMSkill 现有体系中有两层约束：

1. **编排链**：`/pm-need` → collect → refine → 审计门 → prd → sketch 的显式调用序列
2. **行为纪律**：每个 Skill body 中的操作规则（如 refine 的 8 维推断、prd 的追溯规则）

实测发现仅靠「行为纪律」无法稳定产出高质量 PMContext——LLM 在缺乏结构约束时容易跳步、遗漏关键维度、或产出不可追溯项。需要一个**结构层约束**来补充现有行为层。

目标是：**在不改变外显交互（UX 零变更）的前提下**，为每个 Skill 注入一套隐式推理协议，让 LLM 的思考过程有结构、有依赖、可审计。

## Decision

### 1. 双层注入模型

| 层 | 命名 | 本质 | 落盘 | 可见性 | 约束对象 |
|----|------|------|------|--------|---------|
| 心智层 | **PM Thinking Loop** | 6 步隐式推理协议（内在思维框架） | 不落盘 | PM 不可见 | LLM 的思考过程 |
| 流程层 | **Process Chain** | 6 步在现有 Skill 编排链上的显式切片 | `.loop/` 目录 + 摘要回灌 PMContext | PM 主路径不可见，可事后审计 | 每步的产出与依赖 |

### 2. PM Thinking Loop 6 步漏斗

每一步是 LLM 内部的思考约束，要求**显式产出结构化的中间工件**（落盘到 `.loop/`），且**下一步必须消费上一步的产出**。

| 步 | 名称 | 承载 Skill | 产出约束（心智链增量） | 依赖检查 |
|----|------|-----------|----------------------|---------|
| 1 | **理解** (Understand) | `/pm-collect` | 必须产出**问题重构**：把用户输入重述为结构化问题陈述（谁/什么/为什么/约束） | 无前置依赖 |
| 2 | **建模** (Model) | `/pm-refine` 前半 | 必须产出**领域模型片段**：实体/关系/不变量，且必须引用步骤 1 的问题重构 | 实体是否覆盖步骤 1 的问题域？遗漏则补 |
| 3 | **方案** (Solution) | `/pm-refine` 后半 | 必须产出**方案候选集**（≥2 个）+ 各自的适用条件 | 方案是否覆盖步骤 2 的实体？是否满足不变量？ |
| 4 | **权衡** (Trade-off) | `/pm-refine` + 审计门 | 必须产出**决策表**：每个权衡点选了哪个方案、为什么、代价是什么 | 决策是否消解了步骤 3 的方案冲突？ |
| 5 | **风险** (Risk) | `/pm-premortem` | 必须产出**风险清单**：按步骤 4 的决策逐条检查"如果这个决策错了会怎样" | 风险是否覆盖步骤 4 的所有决策点？ |
| 6 | **交付** (Deliver) | `/pm-prd` + `/pm-sketch` | 必须产出**交付物清单**：每项交付物追溯到步骤 4 的哪个决策 + 步骤 5 的哪个风险已处理 | 是否有未追溯的交付物？是否有未处理的风险？ |

### 3. 三件套：输入必须有依据，转换必须有工具，输出必须有追溯

每个步骤的每项产出，必须附带 **审计三元组（Audit Triple）**：

```
<依据集: [材料X, 步骤N-1产出Y, ...]>
  → [工具: /pm-refine, 规则: 8维之"用户场景"]
  → [转换: 从材料X的事实推断用户角色]
  → <产出: 用户场景陈述 + [假设]置信度7>
```

- **依据集**：该产出的上游依据——必须是已落盘的文件/项，不能凭空产生
- **工具与技术**：用哪个 Skill、哪条规则做了转换
- **转换操作**：从依据到产出经历了什么推理步骤
- **产出**：结果 + 标记（事实/[假设]/[待确认]/[冲突]）+ 置信度

完整审计三元组写入 `.loop/<skill>-step<N>.md`（中间工件）；**摘要**（决策点+依据数+工具名）回灌进 PMContext「决策日志」表。

### 4. 中间工件的 Entity 身份

**中间工件不是 Entity，是 PMContext 的构建快照**（Construction Snapshot）：

- 有身份（可被下游 Skill 引用）✅
- 有持久化（落盘到 `.loop/` 目录）✅
- 可丢弃（PMContext 成熟后可清理）✅
- 不是永久领域概念（不进 CONTEXT.md Language 段）✅

**PMContext 仍是唯一 Entity**（ADR 0004 不变）。

### 5. 中间工件中达阈值的关键信息自动回灌 PMContext

回灌机制（β）：

- **触发**：流程链每个 step 跑完后，LLM 自行判断哪些信息达到"关键信息"阈值
- **原子性（Atomicity）与落盘时机**：单个 Skill 内部跨 Step 的回灌在 LLM 上下文内做**原子级叠加（Atomic Stacking）**，不逐步 I/O 写 `pm-context.md`。**仅在该 Skill 执行完毕（Model-Invoked Exit）时**做**单次批量落盘**——避免 step 间反复读写 PMContext 引起的上下文切换与读写冲突
- **约束 1**：回灌落进 PMContext **已有 heading**（「## <页面/功能名>」下的「### 事实/规则/验收」等），不开新 heading
- **约束 2**：回灌信息走现有标记体系（[待确认]/[假设]/[冲突]），来源标注 `← 来源: loop step N`

### 6. Enforcement：Thinking Protocol 段

每个 SKILL.md body 中新增显式段 **## Thinking Protocol**：

```markdown
## Thinking Protocol

本 Skill 承载 PM Thinking Loop 的步骤 [N-M]：

| 步骤 | 本 Skill 的职责 | 产出（是否回灌 PMContext） |
|------|---------------|--------------------------|
| N. <步骤名> | <具体做什么> | <回灌维度 或 "不回灌"> |
| ... | ... | ... |

执行时必须依次完成上述步骤，不可跳过。步骤间产出写入 `.loop/<skill>-step<N>.md`。
达阈值的关键信息自动回灌到 PMContext 对应 heading（不开新 heading、走现有标记体系）。
每项产出必须附带审计三元组（依据集 → 工具/技术 → 产出），完整版落 `.loop/`，摘要回灌决策日志。
```

**放置位置**：SKILL.md body 的「Instructions」段之后、「流程」段之前。

### 7. 流程链与现有编排链的映射（γ 模式）

流程链 6 步是**横切在现有编排链上的全局心智链**，不替换、不嵌套，只是按现有 Skill 职责分工切片：

| 步 | 落地的 Skill | 回灌? |
|----|-------------|-------|
| 理解 | `/pm-collect` | 不回灌（收集原始材料） |
| 建模 | `/pm-refine` 前半 | 回灌 8 维 |
| 方案 | `/pm-refine` 后半 | 回灌优先级+技术约束+方案候选 |
| 权衡 | `/pm-refine` + `审计门` | 回灌决策日志 |
| 风险 | `/pm-premortem` | 回灌假设清单升级 |
| 交付 | `/pm-prd` + `/pm-sketch` | 不回灌（产出 View） |

**重要变更**：`--auto` 模式下，`/pm-premortem` 从「可选独立调用」升级为「流程链第 5 步的强制承载者」，自动编入主链路。

### 8. —auto 模式下主链路升级

旧链路（--auto）：collect → refine → prd → sketch

新链路（--auto）：collect → refine → 审计门（不暂停）→ **premortem** → prd → sketch

premortem 不暂停、不停顿，只在最终的一站式报告中多一行风险摘要。

### 9. 依赖检查失败时的自愈机制（Self-Correction Loop）

依赖检查（如 Step 3 检查方案是否覆盖 Step 2 的实体）失败时，模型处置规则：

- **禁止路径**：直接中止报错、或打 `[待确认]` 标签后继续——这是把半成品当产出
- **禁止路径**：将未通过依赖校验的半成品直接落盘到 `.loop/` 或回灌 PMContext
- **强制路径**：在隐式思考空间（Hidden CoT）内立即触发**回溯自愈（Self-Correction Loop）**——重新生成当前步骤的产出，直至通过依赖检查。自愈轮数有上限（默认 3 轮），超出仍失败则降级为：标 `[待确认]` + 信息缺口记录断链点 + 终止当前 Skill 并告知用户

自愈机制保证产出结构的完整性，避免"形式通过、实质断链"的伪合规。

### 10. `.loop/` 目录的垃圾回收（GC）策略

锁定两条规则，不留待后续 ADR：

1. **`.loop/` 默认写入 `.gitignore`**——中间工件是构建快照，不应污染用户的 Git Commit 历史
2. **Wipe-on-Entry**：每次用户显式调用 `/pm-need <需求描述>`（或 `/pm-need --incremental` 之外的入口调用）时，底层自动对 `docs/pm-context/.loop/` 全量清空，开启一轮干净的思考循环

例外：`--incremental` 模式不清空 `.loop/`，因为增量更新需要消费上一轮的中间工件做差分推断。

### 11. 审计三元组的反形式化敷衍红线

LLM 擅长玩文字游戏——"依据是 A，产出是 A'，转换操作写'我把 A 转换成 A'"这种同义反复（Tautology）能通过格式校验但毫无推理密度。

**高压红线**：转换操作（Transformation Method）必须阐明**具体推导逻辑**，例如：

- ✅ 同义词推导（"用户说'账号'，依据 glossary 映射为'Customer'实体"）
- ✅ 多对多实体映射（"材料 M1 的角色 R 与 M2 的权限 P 关联，推导出新实体 Customer-Role"）
- ✅ 边界隔离分析（"硬件限制 H1 与方案 S2 的延迟约束冲突，需隔离到独立模块"）
- ❌ "将 A 转换为 A'"、"基于上述依据产出"、"经过分析得到"——这些空话判定为 Failure

**检测机制**：darwin-skill 的 Phase 1 基线评估中，dim8（实测表现）专项检测三元组的推理密度。形式化敷衍的三元组在该维度直接扣分，触发 Skill 协议本身的自愈重写。

### 12. 决策总结

| 编号 | 决策要点 |
|------|---------|
| 1 | 双层注入：心智链（不落盘）+ 流程链（落盘 `.loop/`） |
| 2 | 6 步漏斗：理解→建模→方案→权衡→风险→交付 |
| 3 | 审计三元组：依据集→工具/技术→产出 |
| 4 | 中间工件是 PMContext 构建快照，不是 Entity |
| 5 | 回灌走 β 机制，**Skill 内原子叠加、Exit 时批量落盘** |
| 6 | Enforcement 通过 SKILL.md 的 `## Thinking Protocol` 段 |
| 7 | 流程链 γ 横切到现有编排链，不替换不嵌套 |
| 8 | --auto 模式 premortem 强制编入主链路 |
| 9 | 依赖检查失败→隐式自愈重生成（最多 3 轮），超限降级标 `[待确认]` |
| 10 | `.loop/` 进 `.gitignore` + Wipe-on-Entry（`--incremental` 例外） |
| 11 | 审计三元组禁同义反复，darwin-skill dim8 检测推理密度 |

## Consequences

### Positive

- PMContext 质量提升：每项产出既有行为纪律约束又有结构约束，跳步/裸奔项可预期减少
- 可审计性增强：审计三元组使整个推理链可追溯、可复审
- UX 零变更：PM 的交互路径不变（/pm-need → 审计门 / --auto）
- ADR 0004（PMContext 唯一 Entity）不动：中间工件不是 Entity
- 原子叠加 + Exit 批量落盘避免反复 I/O，运行性能更稳
- 依赖检查自愈机制杜绝"形式通过、实质断链"的伪合规
- `.loop/` GC 策略锁定，目录不失控、不污染 Git 历史
- 反形式化红线让审计三元组保持推理密度，不退化为文字游戏

### Negative

- 每个 SKILL.md 需增加 Thinking Protocol 段，维护成本上升（改漏斗改 11 处）
- --auto 模式运行时间微增（premortem 强制编入 + 自愈重生成可能多次循环）
- 自愈机制可能放大 Token 消耗——3 轮上限是硬刹车，但仍可能在该 Skill 内消耗 3× 思考成本

### Risks

- Thinking Protocol 如果写成"请仔细思考"之类的空话则零增量——产出约束必须具体到"必须产出 XX 且必须引用 YY"
- 回灌机制依赖 LLM 对"关键信息"的自主判断——阈值不清晰可能导致回灌过少（PMContext 空转）或过多（污染现有结构）
- 自愈机制有死循环风险——已用 3 轮上限硬刹车兜底，但仍需 darwin-skill 实测监控自愈触发频率，频繁自愈说明 Skill 协议本身有问题
- 审计三元组形式化敷衍风险——已用决策 11 的反同义反复红线 + darwin-skill dim8 检测兜底，但 LLM 的"绕过红线"能力不可小觑，需持续质询校准

### 需要同步更新

1. CONTEXT.md — 新增心智链/流程链/Thinking Protocol/中间工件/审计三元组/原子叠加/自愈机制术语，更新 Relationships 和 Skill 调用关系
2. 每个 SKILL.md — 新增 `## Thinking Protocol` 段（根据 Q5 映射表各分配对应步骤）
3. 产物目录布局 — 新增 `.loop/` 目录
4. `.gitignore` — 追加 `docs/pm-context/.loop/`
